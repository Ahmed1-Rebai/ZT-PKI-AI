# Performance and A/B/C/D evaluation

Last measured on 21 Nov 2026 in the VirtualBox 7.1 lab (virtio NICs, 2-vCPU gateway); first campaign on 11 Oct 2026.
Raw data: [perf.json](perf.json), [perf-abcd.json](perf-abcd.json), [abcd/](abcd/).
Tables and charts: [results.md](results.md), regenerated by `make_report.py`.

## 1. How it was measured

| Script | What it measures |
|---|---|
| [`tests/perf/perf.sh`](../perf/perf.sh) | iperf3 (TCP, 4 streams, 10 s, median of 3): plain link, OpenVPN tunnel, full ZT path; ping RTT; OpenVPN connect time; PDP `/v1/authenticate` latency (20 calls, median); gateway CPU |
| [`tests/perf/perf-abcd.sh`](../perf/perf-abcd.sh) | the **same forwarded path** (tunnel → gateway → web-app) in configs A, B, C, D, plus D without the traffic mirror |
| [`tests/abcd/set-config.sh`](../abcd/set-config.sh) | switches the lab between A (perimeter VPN), B (static per-role ZT rules), C (dynamic PDP, no AI), D (PDP + AI, normal state) |
| [`tests/abcd/probe.sh`](../abcd/probe.sh) | exposed-surface matrix: one connection attempt per service from alice's tunnel (no scanning) |

The deny-by-default policy blocks iperf3, so the scripts insert temporary rules
tagged `zt-perf` and remove them afterwards. The scripts confirm none are left.

The differences between A, B, C and D are within run-to-run noise: the order
changes from one campaign to the next, and no Zero Trust configuration is
slower than A in either. This is expected: established flows take the
`ct state established` fast path in every config, so set lookups, the PDP and
the AI engine are not on the per-packet path. The PDP only acts when a session
opens or when it is re-scored. The AI engine runs on the sensor, off-path.

## 3. Where the throughput goes

Absolute numbers are low (3.9 Gbit/s plain, 312 Mbit/s tunnel, about 30 Mbit/s
forwarded). The cause is the gateway VM, not the Zero Trust logic:

* One gateway vCPU saturates (about 82 %, observed on 11 Oct) while the other idles, so the
  40–45 % average hides a single-core bottleneck. The receiver (web-app) sits at about 2 % CPU.
* That core carries OpenVPN's userspace crypto (`dco_enabled 0`), the routing
  between zones, and the `tc mirred` copy of every zone NIC to the sensor.
* Turning the mirror off gives about 2.2× the throughput (32.5 → 70.8 Mbit/s on 21 Nov,
  37.1 → 93.7 on 11 Oct).
  VirtualBox has no switch port mirroring, so the copy is done in software on
  the gateway.

**Conclusion (H4).** Identity-based, dynamic and AI-driven access control adds
no measurable data-path overhead (≤ 15 % target met). The visibility layer
(mirror) is what costs throughput in this lab. Remedies, in order of effect:

1. Mirror at the hypervisor or physical switch (SPAN / vSwitch port mirroring)
   instead of on the gateway. This removes the mirror cost (54–60 %).
2. OpenVPN DCO (kernel data channel) or WireGuard. This
   removes the userspace crypto copy.
3. RPS/RFS or more gateway vCPUs, to spread the work over several cores.

## 4. A/B/C/D: exposed surface from an employee tunnel

| Service (alice, employee) | ZT expects | A | B | C | D |
|---|---|---|---|---|---|
| Reverse proxy 443 (mTLS) | allow | open | open | open | open |
| web-app 8080 directly (proxy bypass) | deny | **open** | blocked | blocked | blocked |
| web-app SSH (admin only) | deny | **open** | blocked | blocked | blocked |
| PostgreSQL 5432 | deny | **open** | blocked | blocked | blocked |
| Issuing CA SSH (mgmt) | deny | **open** | blocked | blocked | blocked |
| SIEM dashboard (mgmt) | deny | **open** | blocked | blocked | blocked |
| PDP posture channel | allow | open | open | open | open |
| **ZT violations** | | **5** | 0 | 0 | 0 |
| Rights expire on their own | | – | no | yes (TTL) | yes (TTL) |

A classic VPN exposes the database, the PKI and the SIEM to any authenticated
user, which is exactly the lateral-movement path ZT removes. B, C and D expose
the same surface to a legitimate user. They differ in what this benign probe
cannot show:

* **B**: rights are permanent. They survive a PDP outage, a stolen device and a
  bad posture, and nothing re-evaluates them.
* **C**: rights are decided per session, depend on posture, expire after 10 min
  without renewal, and are pulled on revocation or kill.
* **D**: C plus continuous behavioural scoring: anomalous traffic leads to
  restricted, quarantine or revoke without a human.

Under attack (`tests/abcd/attack-abcd.sh`, 21 Nov): the out-of-role SSH (S7)
is exposed in A and blocked in B, C, D; the stolen certificate on a
non-compliant device (S8) keeps its access in A and B and is quarantined in C
and D. See [results.md](results.md).

## 5. Findings fixed during the evaluation (re-tested)

| # | Finding | Fix | Evidence |
|---|---|---|---|
| F1 | A new device without a posture record was refused the tunnel, so it could never send the posture report that admits it | Tunnel admission now uses the policy's `admit` (identity only). An admitted device without good posture gets **quarantine** (posture channel only), and its posture report re-scores it straight away | Live: posture record deleted → reconnect → `quarantine {10.8.0.10, 30m}`, `allow_web` empty → posture report → `allow_web {10.8.0.10, 10m}` within 2 s |
| F2 | `/v1/events` applied the score tier without checking `allow`, so a good AI score could restore rights while posture was failing | Every endpoint and the renewal loop use one `effective_tier()`. If access is not allowed, the tier is at most quarantine | `test_ai_event_never_grants_more_than_policy_allows` |
| F3 | Revoke and kill stopped at the first failing step, so if rule removal failed, the tunnel stayed up | `terminate()` runs both steps independently and logs each failure | `test_revoke_kills_tunnel_even_if_rule_removal_fails`. Live kill: alice removed from the OpenVPN client list, re-admitted by the PDP on reconnect |
| F4 | A critical, burst-confirmed AI event was smoothed by the EMA (α = 0.4): from a clean state it took about 5 more reports to reach the floor rule, which slowed TTQ | A critical event applies its observed anomaly immediately. Normal events stay smoothed | `test_critical_event_revokes_rights` |
| F5 | A VPN client could trigger a gateway SSH call with every posture report | Posture-triggered re-scoring only enforces on a tier change | code review, unit tests |
| F6 | `vpn/scripts/verify.sh` still expected M2 bootstrap mode and flagged the posture channel as a leak; it also left the managed tunnel down | Checks updated for enforced mode; the managed tunnel is restored at the end | 9/9 PASS |

PDP unit tests: 14 passed (10 before these fixes).
